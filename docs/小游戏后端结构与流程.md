## 1. 采用的方案

在现有 ThinkPHP 项目中增加 game 应用，微信小游戏与 TapTap 小游戏调用同一套 HTTPS API。沿用 admin 管理后台、权限菜单、响应风格和数据库访问方式；游戏领域服务放在 common/game，供 game 和 admin 共用。

数据库保存账号、资源、养成、进度、领取记录和操作流水。战斗渲染、移动、子弹、特效继续在 Cocos 客户端执行。游戏服务器确认资源的获得与消耗，客户端不能直接覆盖余额和领取状态。

当前范围不包含现金支付。已有支付依赖不作为本次小游戏功能的接入目标。

## 4. 账号与平台登录

### 4.1 UID 规则

沿用 kr_user.id 作为玩家 UID，接口中以字符串输出。账号表保留昵称等已有字段，新增玩家的 mobile 为 NULL，不创建虚假手机号。

新增 kr_game_identity：

- provider：wechat_mini 或 taptap_mini；
- app_id：对应平台注册的应用 ID；
- openid：服务端向对应平台验证后获得；
- user_id：关联 kr_user.id；
- unionid：可选，仅在所属平台命名空间中使用。

provider + app_id + openid 唯一。平台 identity 的 ID 永远不能当作游戏 UID。首个登录事务同时创建账号、身份、初始存档和钱包，并记录新手初始化结果。并发创建发生唯一键冲突时，失败方回滚整笔初始化，再读取已存在身份；不留下孤立用户，也不再次使用已经消费的登录 code。

### 4.2 登录流程

~~~mermaid
sequenceDiagram
    participant C as 小游戏
    participant G as game/AccessController
    participant P as 微信或TapTap
    participant D as MySQL
    C->>P: wx.login 或 tap.login
    P-->>C: 临时 code
    C->>G: POST /game/v1/auth/{provider}
    G->>P: 服务端验证 code
    P-->>G: openid 与平台会话信息
    G->>D: 事务中查找或创建身份、玩家、初始状态
    D-->>G: UID
    G->>D: 创建游戏登录会话
    G-->>C: UID、Bearer 凭证、有效期
    C->>G: GET /game/v1/bootstrap
    G-->>C: 服务器时间、配置版本、权威存档、revision
~~~

游戏采用独立的 GameSessionService，生成随机 Bearer 凭证，数据库只保存摘要、身份归属和过期时间。管理员继续使用原有 JWT。GameAuth 验证会话、玩家状态及撤销状态，并注入 UID 和已验证渠道；不接受请求正文中的 UID 或 platform 作为权限依据。

初版会话有效期可沿用一天的产品体验；过期后重新平台登录。网络超时的登录重试可以重新获取 code，身份唯一索引保证不会新建重复账号。平台 code、session_key、AppSecret 不写入客户端存档或普通请求日志；不将平台 session_key 用作游戏 Bearer 凭证。仅当后续平台能力确实需要时，在服务器加密保存 session_key。

新增平台 HTTP 客户端校验证书、限制超时并检查响应结构。现有 thirdconnect/GatewayBase 关闭了证书校验，小游戏身份验证不直接沿用该网络行为。平台网络调用放在数据库事务之外。

### 4.3 两个平台是否互通

默认按各自身份建立账号；账号表结构预留多身份关联。只有验证双方账号归属并明确完成绑定后，才共用一个 UID。

账号绑定不是第一期必须开放的功能。后续采用短时、一次性绑定凭证和双方已登录会话确认。若两边已有有效进度，先形成迁移预览：选择目标存档，处理领取记录与限额，记录审计，再执行迁移。禁止通过昵称、头像、客户端填写的手机号或跨平台 unionid 自动合并；禁止简单相加两份余额。尚未实现迁移规则时返回 ACCOUNT_LINK_CONFLICT。

## 5. 数据保存与资源结算

### 5.1 权威数据分层

- kr_game_state：关卡、装备、养成、功能解锁、教程、签到摘要及玩法次数等模块状态。
- kr_game_wallet：金币、钻石、星石、紫币、宠物币、旅行券和核心。钱包是资源余额唯一来源。
- 领取明细：签到、兑换等永久业务去重证据。
- kr_game_ledger：资源增减流水。
- kr_game_request：请求摘要及结果，处理重复提交和响应丢失。

内部拆表不要求客户端立即重写全部展示模块。SaveV3Assembler 从同一数据库快照中组合上述数据，输出兼容现有 version=3 的客户端存档。客户端缓存保存这份结果；恢复时使用服务器 revision 判断新旧。

bootstrap/state 读取必须保持同一一致性快照，不能把先读到的旧装备与稍后读到的新余额拼成一份存档。初版对同一玩家的写入统一先锁 kr_game_state 行；只读使用短事务的一致性快照。

### 5.2 写入类型

| 操作 | 请求内容 | 服务器处理 |
|---|---|---|
| 签到、兑换码 | 请求编号、兑换码等业务输入 | 服务器决定资格、金额和领取状态 |
| 抽武器、抽宠物、买皮肤、升星 | 操作、目标、数量、期望 revision | 校验资格和价格，生成随机结果，扣资源并保存结果 |
| 合成、换装、装备宠物 | 位置或实例引用、期望 revision | 校验拥有关系、锁定与派遣约束，变更状态 |
| 主线、矿场、挑战结束 | 服务器签发的 run_id 与结果证据 | 校验资格、时长和进度，计算允许奖励，结束 run |
| 偏好保存 | 明确白名单的偏好字段 | 只保存无收益影响的偏好，不能携带资源、图鉴或进度 |
| 旧档导入 | 原档及迁移申请 | 独立受控入口，限制资格、次数和可迁入内容 |

由装备状态推导的战力、升级价格、奖励金额不由客户端指定。自动合成开关等会触发玩法行为的设置归业务命令；音量、画质等设备偏好可继续只存在本机。

### 5.3 统一事务流程

1. GameAuth 确认玩家与渠道；Validator 验证请求大小、字段和类型。
2. 开启事务并锁玩家 state 行，检查 request_id。
3. 已有相同 action/参数摘要则返回已提交结果；相同编号配不同参数返回 409。
4. 对结构性命令检查 expected_revision；签到、兑换按当前权威状态和业务唯一键校验。
5. 校验活动、次数、余额、库存等条件；涉及兑换时按固定顺序锁批次和码。
6. 调用 EconomyService 变更钱包，更新模块状态，写领取记录和资源流水。
7. revision 加一，保存请求结果；提交事务。
8. Service 返回普通结果，Controller 再调用 success。

所有写路径遵守同一锁顺序：玩家 state → 活动/兑换批次 → 兑换码 → 钱包 → 明细/流水/请求回执。后台批次操作不在持有批次锁后再反向等待玩家锁；涉及多个玩家的迁移按 UID 排序加锁。死锁进行有上限的整笔事务重试。

业务失败回滚全部变更。响应丢失时重用原 request_id 查询或重试；不得因为没有收到响应就再次本地加钱。回执的大响应可归档，但永久保留最小请求去重键；签到、兑换、run 另外保留业务唯一记录，防止换请求号重复领取。

## 6. 签到与兑换码

### 6.1 每日签到

按服务器 Asia/Shanghai 日期划分每日，不读取设备日期或 testTimeOffsetMs。签到采用现有七次领取后循环的规则；中间漏签不会自动清零，不擅自改成连续签到。

服务器锁玩家状态，检查活动和当天领取记录，确定下一项奖励。一次事务内写入签到明细、更新 lastClaimDay/checkNum/totalCheckNum、增加钻石、记录流水和请求结果。

当前奖励来自 EconomyConfig.ts 的 dailyCheck 配置。每次领取记录实际配置版本及奖励快照；活动调整不重置已有进度。第一版只有一个长期签到活动，使用稳定 activity_id，配置发布版本变化不能变成重新领取的理由。以后同时开多个签到活动时，摘要也按 activity_id 分开，不能共用一个 dailyCheck 计数。

### 6.2 兑换码

后台创建批次：选择奖励预设、有效时间、允许渠道、限领方式，再生成公共码或一批单次码。

玩家提交兑换码后，服务器校验码状态、时间、渠道、批次领取记录和剩余次数，在同一事务内更新额度、领取明细、余额和流水。

第一版约定一个批次每个 UID 限领一次；不同批次可以分别领取。公共码允许多人使用，单次码最大使用次数为一。若以后需要同批次每人 N 次，须增加受锁保护的个人批次计数并调整唯一约束，不能只删除索引。

码和批次的启停、有效期等由服务端判断；渠道取登录身份。通用活动在已绑定的共同 UID 下跨端防重。未绑定的两个 UID 无法仅凭平台身份识别为同一自然人。

## 7. 当前配置和大数的处理

遵守 Project/AGENTS.md：所有资源产出数值继续以 Project/assets/scripts/core/EconomyConfig.ts 为维护入口。构建时导出版本化 JSON 供 PHP 读取，同时生成客户端展示配置；以内容摘要校验版本。购买价格、战斗数值等来自现有各自配置，单独导出并记录组合版本。

后台初版只能选择已发布奖励预设、调整活动时间/渠道/启停，不能另写一份奖励金额覆盖代码配置。当前兑换码的金额进入奖励预设，码清单迁入服务端，客户端产物不再包含有效码清单。

金币和紫币继续使用 digits/exponent/precision 表示。不转换为 PHP float、MySQL DOUBLE 或固定精度 DECIMAL，也不把极大指数展开成巨长整数。PHP 大数实现必须保持现有有效位、取整和截断顺序，使用客户端计算结果生成固定样例，与服务端逐项对照。

其他整数资源保持当前 JavaScript 安全整数范围；API 的 UID、revision、流水 ID 用字符串。旧档中的大数字段按已有验证规则校验，同时增加接口体积和计算预算。

## 8. 与当前 Cocos 客户端的衔接

新增平台适配层：login、request、storage、前后台生命周期；微信和 TapTap 分别实现。UI 调用同一 GameApiClient。

当前 EconomyStorage 是同步 getItem/setItem 接口，多处本地事务依赖写入后立刻读回确认，不能直接把 setItem 换成异步 HTTP 请求。保留其本地缓存用途，另设异步 ServerCommandGateway：

- 启动顺序变为：平台登录 → bootstrap → v3 状态装载 → 展示游戏。
- claimDailyCheck、redeemCode、资源消费等逐个改成异步命令，UI 增加请求中、失败和重试状态。
- 成功后应用服务器确认的状态和 revision，移除这些路径中的本地重复发奖。
- 多个响应乱序时只应用更高 revision；旧回执只能确认操作完成，不能回写旧余额。
- 启动或重连未取得有效云档时，不自动创建空档覆盖云档。
- 断线期间可展示缓存和继续非结算演示；正式资源、购买和领取等待服务器确认。

保存频率按业务划分：领取与消费立即事务提交；普通主线收益按短批次或波次结算，不按每个击杀落库；偏好合并同步；切后台仅补一次尽力同步，不能依赖关闭时上传。

## 9. 战斗、离线与第一版边界

正式上线前，同一个钱包的所有增减入口都必须接管。只迁签到/兑换但仍开放任意钻石写入的客户端存档接口，不算完成服务器结算。

本地战斗初版可保留结果校验：服务器创建 run，绑定玩法、开始时间、资格、配置版本及可信状态，限制每个玩家并发的可获奖场次；升级和换装等中途操作由服务器记录，避免简单冻结属性改变现有玩法。结算按这些可信输入检查进度与奖励上限，run 只能结算一次。客户端结果校验不能提供完全防战斗作弊的保证；严格验证需进一步重算或回放。

离线逻辑不能直接改成“离线秒数 × 每秒金币”：当前 OfflineProgressSimulator 还包含历史关卡重放和自动升级。服务端迁移时保持原计算规则，使用服务器结算游标与时间上限，防止在线结算与离线区间重复覆盖。重新登录后的未结算 run 必须先完成受控关闭或恢复，再计算离线收益。

现阶段广告默认关闭，继续保持。未来启用时按平台实际可用能力接入验证；服务器 nonce、限次和客户端播放完成回调不能单独证明真实观看，不把客户端回调称为服务端广告验证。

## 10. 管理后台与运维

在现有 admin 下增加玩家查询、兑换码管理、签到记录、资源流水、迁移申请。每项接口登记 kr_menu / kr_menu_api / kr_role_menu，沿用 admin_auth、admin_permission。

新增补偿功能时只允许选择预设、填写原因并通过 EconomyService 发放；每笔有独立业务号、操作者和审计记录。不能开放通用“修改存档 JSON / 钻石余额”编辑器。普通恢复备份不能回滚领取记录后重新发奖。

配置与部署：

- 公共 API 经 HTTPS 到同一 PHP 应用，两平台分别配置域名；资源文件继续走现有 CDN。
- 测试和正式环境使用独立数据库与平台配置，不允许客户端参数选择生产/测试环境。
- AppSecret 等保存在服务器配置中，不使用普通运营配置表向客户端下发。
- 新迁移文件放 database/migrations；现有 public/kr_bdf.sql 在上线包中移出公开目录或禁止下载。
- 数据库备份与恢复必须演练，保留领取明细、资源流水和配置历史。
- 初期单应用加数据库足够；多实例时再接共享限流/缓存，事务正确性不依赖单机文件锁。

## 11. 实施顺序与验收

| 阶段 | 交付 | 验收门槛 |
|---|---|---|
| 0：环境与数据准备 | PHP 8 环境、锁定依赖安装、实际库结构确认、备份、增量迁移 | 干净测试库可初始化；现有 admin/wxapp 仍能运行 |
| 1：账号与云端骨架 | game 路由、双方平台 Provider、UID、会话、state/wallet、配置导出 | 并发首次登录不建重复账号；跨用户访问被拒绝；云档不会被空本地档覆盖 |
| 2：签到与兑换闭环 | EconomyService、幂等、领取明细、后台活动管理 | 重复点击、并发、响应丢失、跨日、过期码和额度竞争都不多发/漏发 |
| 3：其余经济入口 | 抽取/购买/合成/升星/转生、玩法结算、旅行、离线 | 所有同钱包路径使用服务器结算；客户端大数样例与 PHP 结果一致 |
| 4：迁移与双端上线 | 旧档受控导入、真机联调、监控、回滚演练 | 微信与 TapTap 各自登录/重连/后台切换通过；配置与经济规则一致 |

阶段 1、2 可以在测试环境独立验收；正式接管现有完整游戏经济必须完成阶段 3。没有迁好的玩法使用明确开关，不开放任意余额上传作为临时通路。

旧档迁移保留原始备份，校验 v3 结构和目录版本，核对已有领取记录。仅凭客户端旧档无法证明历史奖励合法，生产自动导入默认关闭；通过明确的测试玩家名单或人工迁移政策开放。每个 UID 只能迁移一次，迁入余额生成导入流水。已有云端经济活动的账号不能被整档覆盖。

至少覆盖：事务中断全回滚；相同请求不同参数冲突；两个设备同时消费；不同请求号重复签到；共享码最后额度竞争；旧 revision；24 点跨日；漏签后继续；离线重复领取；测试时间污染；两份存档绑定冲突；后台补偿审计。
