# 奖励后端核验

离线收益、每日签到、每日分享、兑换码通过 `/game/v1/rewards/*` 结算，使用现有微信登录 Bearer 会话和玩家 UID。客户端不提交奖励金额、离线时长或领取日期；请求中的额外字段会被拒绝。奖励余额、领取记录、云存档版本、历史快照和幂等回执在同一 MySQL InnoDB 事务内提交。

## 部署

1. 部署本次 PHP 源码、`database/migrations/003_game_rewards.sql`、`database/migrations/004_game_share.sql`、`config/rewards-economy.json`、整个 `bin/reward-runtime/` 及 `bin/reward-worker.cjs`。分享版本的配置必须包含导出的 `dailyShare`。
2. 安装 Node.js 20 或更新版本；PHP 8 必须允许 `proc_open`。PHP 运行用户应能执行 Node 并使用系统临时目录。Node 不需要安装 npm 依赖。
3. 执行 `php think game:migrate`。该命令幂等创建新增奖励表，不重置已有玩家、存档或领取记录。
4. `[GAME]` 可配置 `NODE_BINARY = /usr/bin/node` 和 `REWARD_TIMEZONE = Asia/Shanghai`。Windows 使用 PHP 服务账户可访问的 Node 可执行文件绝对路径。签到和分享共用该日界，时区上线后应保持稳定。
5. 重新构建并发布匹配当前存档结构和奖励接口的客户端。上线版不支持旧存档导入、缺账本快照或旧客户端省略分享字段的协议。

奖励数值的唯一来源仍是 `Project/assets/scripts/core/EconomyConfig.ts`。在 Project 运行 `npm run rewards:export` 导出 JSON 配置和 Node 纯算法模块；`npm run rewards:check` 检查产物是否过期。不要直接编辑生成文件。离线收益复用现有 `OfflineProgressSimulator`，保留大数精度、自动升级、历史关卡重放、离线时间上限和遗物加成。worker 要求合法的金币 `digits/exponent/precision` 及当前转生、宠物、皮肤、鱼、能力区块，不推断缺失精度或以默认状态跳过损坏区块。

站点文档根目录仍为 `public`。生成配置与 Node 文件位于文档根目录之外。

## 接口契约

所有成功响应包含 `player_id` 和服务端配置的 `namespace`；所有接口均要求 `Authorization: Bearer <access_token>`。POST 的 Content-Type 为 `application/json`。

| 方法与路径 | 参数 | 用途 |
|---|---|---|
| `GET /game/v1/rewards/state` | 无 | 返回服务端签到、分享状态及下一次日界时间 |
| `POST /game/v1/rewards/daily` | `request_id`, `base_revision`, `day_index` | 领取当前可领签到日；`day_index` 为 0 到 6 |
| `POST /game/v1/rewards/share` | `request_id`, `base_revision` | 领取当日分享奖励；与签到额度独立 |
| `POST /game/v1/rewards/redeem` | `request_id`, `base_revision`, `code` | 核验并兑换配置中的兑换码 |
| `POST /game/v1/rewards/offline` | `request_id`, `base_revision` | 从数据库内快照和服务端保存时间计算离线收益 |

`request_id` 为 16 至 80 位字母、数字、下划线或连字符；`base_revision` 是云存档版本的十进制字符串。奖励请求必须已有云存档。客户端应在发送前持久化整个请求，网络中断后原样重发，不能换 request_id 再猜测是否领取成功。

状态响应包含 `revision`、`server_time_ms`、`next_daily_reset_ms`、`daily_check`、`daily_share`。`daily_check` 的形状与客户端 DailyCheckSnapshot 一致：`lastClaimDay/checkNum/totalCheckNum/today/canClaim/claimableIndex/blocked/days`。`daily_share` 的形状为 `{lastClaimDay,today,canClaim,blocked,diamonds}`。客户端用服务端的 `next_daily_reset_ms` 刷新状态，不能用设备日期解锁签到或分享。

只有新账号尚无云存档（`save:null`）时，状态查询才提供空签到、分享账本的初始预览；领取前仍须建立完整云档。已有快照缺少或损坏 `dailyCheck` / `dailyShare` 时对应状态为 `blocked`，不当作未领取；兑换也要求有效的 `redeemedCodes`。当前客户端必须校验完整的签到、分享状态，不能将缺字段响应视为旧后端能力降级。

领奖响应包含：

```json
{
  "player_id": "123",
  "namespace": "production",
  "request_id": "daily_request_0001",
  "revision": "18",
  "current_revision": "18",
  "awarded_revision": "18",
  "save": "完整的 v3 云存档 JSON 字符串",
  "saved_at_ms": 1792756800000,
  "server_time_ms": 1792756800000,
  "next_daily_reset_ms": 1792771200000,
  "reward": { "kind": "daily", "diamonds": 140, "dayIndex": 0 },
  "daily_check": {},
  "daily_share": {}
}
```

示例数值仅展示接口结构；实际金额从生成配置读取。`reward` 的形状如下：

- 签到：`{kind:"daily",diamonds,dayIndex}`。
- 分享：`{kind:"share",diamonds}`。
- 兑换码：`{kind:"redeem",diamonds,code}`。
- 离线：`{kind:"offline",result:OfflineProgressResult|null,before:{gold,levels,stageIndex,waveIndex}}`。大数仍为 `{digits,exponent,precision}`；不足最小离线时间时 result 为 null，但会推进服务端检查点。

回执中的 `revision/save` 永远是当前云存档头版本，`awarded_revision/reward` 指原请求首次结算的版本和结果。若重试时已有后续进度，`awarded_revision` 会小于 `revision`；客户端必须采用当前云档并重新进入会话，不能把旧 reward 再加到当前余额。回执永久保留，不随普通存档请求的 30 天保留期清理。

## 每日分享

每日分享默认发放 80 钻、每天一次，数值来自 `EconomyConfig.dailyShare`。服务器按账号、save namespace 和服务器日期去重；平台不参与额度拆分。当前微信端采用拉起分享并返回小游戏作为完成条件，不验证收件人是否实际收到分享；接口负责领取额度和结算，后续其他平台沿用同一奖励接口。

分享记录在 v3 存档中使用必填 `dailyShare:{lastClaimDay}` 镜像，同时以独立的 `game_share_claim` 表保留服务端领取记录。资格采用有效镜像日期与数据库最新领取日中的较晚者；新建存档使用空日期。已有快照缺少镜像、显式 null 或日期非法时禁止领取并保留原数据，不自动重置。数据库的 `(user_id,namespace,day)` 唯一键与钱包、云版本和永久回执处于同一事务，重复点击、重复回调、断网重发和多设备并发都不会重复发奖。

更新时先部署完整后端及生成配置，运行 `php think game:migrate` 创建 `004_game_share.sql` 中的分享表，再更新客户端。已有云档的普通上传必须携带不变的完整奖励账本，省略 `dailyShare` 同样会被拒绝。部署或回滚不得删除分享表与领取记录，客户端和服务端必须保持当前接口契约一致。

## 两类兑换码

在 EconomyConfig.ts 的 `redeemCodes` 中配置 `mode`：

```ts
{ code: '公开活动码', diamonds: /* 原有配置金额 */, mode: 'per_player' }
{ code: '单人礼包码', diamonds: /* 原有配置金额 */, mode: 'global_once' }
```

`per_player` 允许每个账号在同一服务命名空间各领取一次；`global_once` 只允许任意一个账号领取一次。多个账号同时兑换时，服务端锁定相同兑换码行，并以全局唯一索引保障只产生一个领取者。默认现有 `950424` 保持原金额，类型为 `per_player`。

同一个码首次使用后，类型和金额固定；修改会返回 `REWARD_CONFIG_ERROR`，应发放一个新字符串的码。移除配置项可停用未兑换请求，已经成功的 request_id 仍能恢复回执。领奖规则按 save namespace 隔离，测试环境不会消耗生产环境礼包码。不要直接删改 `game_redeem_claim`、`game_daily_claim`、`game_share_claim` 或 `game_reward_request` 来重发奖励。

## 并发与存档边界

普通上传和奖励结算均先锁定同一 UID，再检查云存档 CAS 版本。旧版本上传不能覆盖新奖励。普通 `/save` 上传会检查已有快照和候选快照的 `dailyCheck`、`dailyShare` 和 `redeemedCodes` 均存在且相同，禁止更改已存在的服务器领奖记录；客户端遇到 `REWARD_STATE_CONFLICT` 应重新读取并使用有效云端存档。合法普通上传仍保留原文字节，不通过注入默认字段修复输入。

新账号由客户端创建完整当前结构及初始账本，不提供旧本地存档导入。当前存档的领取记录始终保留，后续领取资格由服务器核验。其他在线玩法目前仍上传客户端快照，本次并未把所有金币、道具和战斗过程都改为服务器权威。离线计算使用已存储快照中的战力和等级，并非对历史在线战斗的完整反作弊校验。

离线输入时间仅来自 `game_save.saved_at_ms` 与服务器当前时间。客户端 `offline.lastSavedAtMs` 被忽略，首次上传不会按本地旧时间追补。冷启动有本地待补传进度时，`POST /save` 可额外传 `resume:true`：更新快照和版本，同时保留已有的服务器检查点；首次上传仍以服务器当前时间建立检查点。只有 true 合法，普通前台上传应省略此字段并推进检查点。该标记不参与存档请求 hash，已有 pending 请求可用原 request_id 在启动时恢复。

补传不能提供、回拨或生成时间戳；离线结算完成后检查点由服务器推进，再次领取不能重复结算相同时段。`GET /save` 的 `saved_at_ms` 表示最近确认活跃的服务器检查点；`POST /save` 回执的 `saved_at_ms` 表示本次写入实际确认时间，用于原有 30 天重试保留。启动补传时两者可能不同，离线收益只由服务器内部检查点计算。该协议不验证所有在线过程，也不能防止篡改客户端故意停止在线同步；完整经济反作弊需要另行服务器化在线玩法。

Node worker 固定执行部署中的文件，参数不拼接 shell；输入输出使用临时文件避免管道阻塞，执行上限 10 秒、输出上限 3 MiB。计算失败、进程缺失、历史存档写入失败或事务失败均不会发放部分奖励。

## 错误码

| 错误码 | HTTP | 处理 |
|---|---:|---|
| `REWARD_INVALID` | 422 | 请求格式错误或提交了额外字段 |
| `SAVE_REQUIRED` | 409 | 先建立云存档 |
| `SAVE_CONFLICT` | 409 | 读取最新进度，处理多设备冲突 |
| `REQUEST_ID_CONFLICT` | 409 | 同一 request_id 不能改变参数或奖励类型 |
| `REWARD_STATE_CONFLICT` | 409 | 普通上传试图改变领奖记录，使用云端进度 |
| `REWARD_STATE_INVALID` | 409 | 签到、分享或兑换账本缺失/损坏，保留原数据并停止领取 |
| `DAILY_NOT_CLAIMABLE` | 409 | 当天已领或天数不符，刷新签到状态 |
| `SHARE_NOT_CLAIMABLE` | 409 | 当天分享奖励已领或已暂停，刷新分享状态 |
| `REDEEM_INVALID` | 422 | 兑换码不存在或停用 |
| `REDEEM_ALREADY_USED` | 409 | 此账号已用，或全局码已被别人使用 |
| `REWARD_WALLET_LIMIT` | 422 | 钻石余额无效或超过 JS 安全整数范围 |
| `REWARD_CONFIG_ERROR` | 503 | 配置缺失/损坏或已发码被改动 |
| `REWARD_CALCULATION_FAILED` | 503 | 检查 Node 安装、执行权限和 worker 部署，原请求可重试 |

登录和会话的 401/403 错误沿用现有登录接口。

## 验证

```sh
php tests/game/run.php
php tests/game/save.php
php tests/game/rewards.php
php tests/game/share-state.php
php tests/game/share.php
```

测试使用随机 `test_login_*` 表前缀，结束只删除本次测试表，不修改生产玩家。奖励测试覆盖真实 HTTP 鉴权、请求伪造、服务端日期和七日循环、回执恢复、旧存档覆盖拦截、两个账号各领一次、三条独立连接争抢全局码、同请求并发重试、数据库故障回滚、离线时间篡改和 Node 不可用回滚。工作目录需已安装 PHP 依赖、可连接测试数据库，并可通过 `node` 运行生成的模拟器。

`share-state.php` 不连接数据库，检查上海零点日界、请求字段、新账号初始预览及已有快照缺账本的拒绝；`share.php` 还检查每日唯一、并发重试、独立账号和 namespace、配置调整、缺失/损坏账本及省略镜像上传被拒绝、离线 worker 保留记录、钱包上限、事务回滚和真实 HTTP 接口。

便携本机数据库可为测试进程设置 `GAME_TEST_DB_PORT`（1024–65535）、`GAME_TEST_DB_NAME`（`test_` 开头）及可选 `GAME_TEST_DB_PASSWORD`。测试入口会强制连接 `127.0.0.1`，不修改项目 `.env`；HTTP 和并发测试子进程继承这些设置。测试仍仅创建并清理自身随机前缀的表。
