# 云存档（方案 A）

2026-10-23 实现。微信正式环境使用已登录的玩家 UID，通过 PHP 接口同步完整 v3 存档到 MySQL。在线战斗等玩法仍由客户端计算；离线收益、每日签到和兑换码已接入[奖励后端核验](奖励核验接入.md)。云存档提供跨设备进度同步，不代表全部经济流程已经服务器化。

## 数据与接口

基础地址沿用 `/game/v1`，两个接口都必须通过 `GameAuth` 校验 Bearer 会话，UID 只从会话取得。

| 接口 | 请求 | 返回 |
| --- | --- | --- |
| `GET /save` | 无请求体 | `player_id`、`namespace`、字符串 `revision`、`save`、`saved_at_ms`、`server_time_ms` |
| `POST /save` | `request_id`、字符串 `base_revision`、字符串 `save`；冷启动补传可额外传 `resume:true` | `player_id`、`namespace`、`request_id`、字符串 `revision` / `current_revision`、`saved_at_ms` |

没有云档时版本为 `"0"`、`save` 为 `null`，客户端据此创建完整的新账号初始状态。`save` 是整个存档的 JSON 原文字符串，最大 2 MiB。服务器只检查版本、余额、升级、武器和进度的基础结构，原文写入 MEDIUMTEXT，避免 JSON 重编码改变大数或无关字段，不负责完整玩法结构校验。当前客户端要求完整 v3 结构：金币包含合法的 `digits/exponent/precision`，武器为 `catalogVersion: 4`，序列化的各玩法区块、教学计数及奖励账本均存在；离线 worker 也校验其计算所需的精度、武器与玩法输入。恢复或计算遇到缺字段、不支持的格式时拒绝操作，不补齐为新档；不导入旧本地档或执行武器目录迁移。

迁移 `002_game_save.sql` 增加三张 InnoDB 表，默认前缀 `kr_`：

- `game_save`：按 UID、namespace 唯一保存最新快照和版本。
- `game_save_history`：保留首份快照、最近 20 个版本、近 14 个 UTC 日期每天首份快照。
- `game_save_request`：保存请求摘要及回执，保留 30 天。相同请求重复提交返回原回执，内容变化返回 `REQUEST_ID_CONFLICT`。过期请求也受版本校验保护。

写入在同一事务中锁玩家行，比较版本，再提交快照、历史和回执。两台设备同时写同一版本，只有一份成功；另一份返回 HTTP 409 / `SAVE_CONFLICT`。比较服务端版本，不按设备时间或余额大小选档。历史清理在该玩家成功写入时进行。需要更长期灾备时，应另外备份数据库。

已有云档与待上传快照都必须包含 `dailyCheck`、`dailyShare` 和 `redeemedCodes`，普通上传不能改变这些奖励账本；缺失或变更返回 HTTP 409 / `REWARD_STATE_CONFLICT`。首次创建云档提交完整的初始账本。冷启动 `resume:true` 只保留数据库已有的离线时间锚点，不接受任何客户端时间；正常前台上传和领奖结算推进锚点。详细回执时间含义和启动顺序见奖励接入文档。

`[GAME] SAVE_NAMESPACE = production` 由服务器配置，客户端不能指定。测试服务器需要独立数据库或 namespace；当前游戏 test 包不进行云同步，避免测试补给进入正式档。

## 自动保存时机

| 时机 | 行为 |
| --- | --- |
| 新建存档 | 本机落盘后请求保存；首次建立服务端时间锚点 |
| 启动离线结算 | 补传待同步本地进度时使用 `resume:true` 保留服务端锚点，再通过奖励接口结算；确认服务端完整快照后进入 |
| 普通战斗收益、临时增益计时、前台检查点 | 有变化才同步，首次变化后约 60 秒合并上传 |
| 过关、挑战奖励、抽取、购买、转生、旅行派遣/领取等 | 本机保存后以 5 秒防抖、最长 15 秒合并；自动上传距上次成功至少 30 秒 |
| 签到、兑换 | 使用奖励接口原子更新云档，客户端安装已确认完整快照 |
| 切后台 | 先保存本机，再尽力上传；若已有请求在途，完成后再尝试提交余下变化 |
| 回前台 | 云档读取缓存有效期为 5 分钟；需要读取时校验版本，断网保留本机进度并重试 |
| 网络失败 | 保留待上传请求 ID 和原始内容，以 15、30、60…最多 300 秒退避重试 |

回执确认前不会标记同步完成。请求在途时发生的新变化不会因旧回执而被清除。应用被强制关闭时网络请求不保证送达，但已写入的本机缓存下次会继续同步；首次登录/拉云档失败停在重试页，不自动建立新档。

## 本机缓存与冲突

缓存使用一个经写后读回验证的存储记录，包含最近确认的云档版本、确认原文、本机原文以及待重试请求。键包含后端地址、环境、namespace、UID，冲突备份同样按账号隔离。

启动仅恢复当前账号的云档与隔离日志。没有云档、也没有待恢复日志时创建新进度，不读取或绑定旧的未绑定本机档；已有当前日志的未上传进度继续通过原请求恢复。

运行中发现冲突会暂停游戏，显示云端和本机进度。选择本机需要再次确认；两份进度先备份，再按刚展示的云端版本提交。选择云端也保留本机备份。成功后重载场景，重新恢复存档、计算解锁和准备面板。读取过程中若云端再次变化，会重新要求选择。服务器记录丢失或版本退回时，也不能自动抹掉干净的本机缓存。

如果本机与云端领奖记录不同，选择本机也不能覆盖服务端记录；保留本机备份后必须使用含有正确领奖记录的云端进度。

会话续期后 UID 变化会停止同步，旧账号的进度绝不随新账号上传。账号停用、非法存档、持久化失败等会暂停并提示重新进入。不要手工把某玩家 JSON 直接覆盖给另一个 UID。

## 上线顺序

1. 备份服务器数据库和现有 PHP 文件，上传本次后端包，保留服务器 `.env`、`runtime`、上传目录及原游戏静态资源。
2. 在 PHP 项目根目录执行 `php think game:migrate`。命令可重复执行，创建当前所需表；用户表必须使用 InnoDB，`user.last_login_ip` 必须为 `VARCHAR(45)` 以容纳 IPv6。已有结构不符合要求时直接报错，不自动修改旧表，不导入示例账号、不转换玩家存档或替换现有玩家。
3. 确认 `GET /game/v1/health` 为 200；未登录访问 `GET /game/v1/save` 和 `POST /game/v1/save` 必须为 401，而不是 404。反向代理保留 Authorization；如提高大档上限，HTTP JSON 转义后的请求可能接近 12 MiB，需要相应请求体限制。
4. 部署成功后再更新微信客户端。新客户端会等待 `/save`，旧后端的 404 会阻止进入，因此不能只更新小游戏代码。
5. 使用真实微信账号验证：新账号初始化、当前存档重进恢复、另一台设备恢复、断网操作后补传、两设备冲突、切账号隔离，以及不支持格式被拒绝且原数据未被覆盖。

网页预览和 test 包保持本地存档；TapTap 等尚无真实登录适配器的渠道不会启用云存档。当前代码不会替玩家新建账号登录网页。

## 验证与恢复

客户端运行 `npm run check`；后端运行 `php tests/game/run.php` 和 `php tests/game/save.php`。后端测试创建随机 `test_login_…_` 表，覆盖鉴权、并发首次保存、版本冲突、幂等回执、事务回滚、原文精度和历史保留，结束只删除自身测试表。

历史快照供运维恢复使用，本期没有对外开放任意版本覆盖接口。恢复时先备份当前数据，选择目标快照，经当前版本校验写为一个新版本，保留原历史；不要降低或复用 revision。客户端冲突备份保存在对应 UID 的 `:backup:` 键下，未自动删除。

本地通过不等于线上发布。交付时的实际构建、测试和线上检查结果见交付目录的验证记录。
