设计日期：2026-10-23  
适用：E:/gunner/PHP 的拟新增 game 应用  
上层设计：[结构与流程](小游戏后端结构与流程.md)

本文保留服务器权威后端的目标数据契约。2026-10-23 已实现登录相关表/API，以及独立的 `game_save`、`game_save_history`、`game_save_request` 和 `GET/POST /save` 快照同步接口。迁移 `001_game_login.sql`、`002_game_save.sql` 均由 `php think game:migrate` 运行。快照方案契约见[云存档接入](云存档接入.md)；下文其余权威结算表和 API 尚未实现。

2026-10-24 当前接入范围以[云存档接入](云存档接入.md)和[奖励核验接入](奖励核验接入.md)为准，奖励表由 `003_game_rewards.sql`、`004_game_share.sql` 创建。当前只支持完整的现行存档及奖励接口；下文 `save-import` 与旧档迁移表属于早期设计，已从本次上线范围撤除，不提供旧档导入入口。

## 1. 数据库通用约定

- 下文沿用 SQL 导出中的 kr_ 前缀；实际迁移取部署配置，不在代码里重复拼接前缀。
- 游戏事务表使用 InnoDB；新增表使用 utf8mb4。平台标识、令牌摘要、请求号、兑换码摘要使用二进制或明确区分大小写的比较规则。
- 目标数据库必须支持 JSON 和所需 InnoDB 行锁；实施前确认真实 MySQL 版本。约束由服务端校验与唯一索引共同保证，不假定导出文件就是线上结构。
- 游戏新表的 create_time/update_time 沿用项目秒级字段习惯；精确结算时间另设 *_at_ms 为 BIGINT；业务日使用 DATE，按 Asia/Shanghai 计算。
- user_id 与现有 kr_user.id 使用相同 UNSIGNED INT 类型；若将来扩容 ID，相关表一起迁移。
- 原始客户端对象和请求不能直接 Model::create/update；经过白名单 DTO 后写入。
- 内部存档 schema_version 与客户端存档 version=3 分开，revision 表示权威状态变更顺序。revision 在接口中是十进制字符串。
- 所有领域写操作先锁玩家 state 行；事务使用同一个数据库连接。

## 2. 表结构

### 2.1 复用 kr_user

保留 id、nickname、mobile、avatar、status、登录时间和软删除字段。游戏首次登录可创建 mobile=NULL 的用户。

前置迁移：若真实表仍是 MyISAM，备份后转换 InnoDB。不要将 MyISAM kr_user 与 InnoDB 初始化表放进同一事务后假定能整体回滚。

已有 kr_user_wechat_mini 只作为兼容来源：必须确认旧身份所属的 appid，处理重复 openid、缺失 user_id 和失效用户，再导入通用身份表。没有这些证据不能仅按 openid 合并。旧 wxapp 暂时继续使用旧表；游戏身份只写新表，不做无约束双写。

### 2.2 kr_game_identity：平台身份

| 字段 | 类型／规则 |
|---|---|
| id | BIGINT 主键 |
| user_id | 关联 kr_user |
| provider | VARCHAR(24)，wechat_mini / taptap_mini |
| app_id | VARCHAR(128)，服务端选择的应用配置 |
| openid | VARCHAR(128)，平台验证结果 |
| unionid | VARCHAR(128)，可空，只在所属平台中解释 |
| create_time / update_time / last_login_time | 时间字段 |

唯一索引：(provider, app_id, openid)。第一版一个 UID 在同一 provider/app_id 下最多绑定一个身份，再加唯一索引 (user_id, provider, app_id)。

### 2.3 kr_game_session：游戏会话

id、user_id、identity_id、token_hash CHAR(64)、expires_at_ms、revoked_at_ms（可空）、create_time、last_seen_at_ms。

token_hash 唯一；索引 user_id/expires_at_ms。客户端持有随机原始 token，数据库保存 SHA-256 摘要。不会把平台 code、session_key 或管理员 JWT 放进这一列。关闭玩家后，GameAuth 即使令牌未过期也应拒绝请求。

### 2.4 kr_game_state：模块状态

user_id 为主键；schema_version INT；revision BIGINT UNSIGNED；config_version VARCHAR(64)；state_json JSON；settlement_cursor_ms BIGINT；migration_status；create_time/update_time。接入玩法结算阶段再增加可空 active_run_id，由同一玩家行锁保护。

state_json 保存：

- levels、progress；
- weapons 中的背包、装备、图鉴、升星和自动设置，不含 diamonds/starGems；
- skins；
- pets 中的拥有、装备、图鉴和次数，不含 coins；
- fish、hunt、mine、buffs；
- rebirth 中的等级、次数和领取限制，不含 ruby；
- speedRun、boss、raid；
- adventure 中的等级、经验、行程、计时和次数，不含 cores/tickets；
- relics、content、tutorial；
- dailyCheck 摘要，内容为 lastClaimDay/checkNum/totalCheckNum；第一版对应一个固定签到活动。
- 可选 preferences，对应后续明确需要跨设备同步的无经济影响 UI 偏好；与 v3 玩法存档分开输出。未定义具体白名单前不开放 /preferences。

当前版本中的 catalogVersion 等子模块版本继续保留。每日限制字段由服务器维护，不作为客户端可上传内容。offline.lastSavedAtMs 在 DTO 中由服务器结算游标生成；其具体推进规则由在线/离线结算服务统一维护。testTimeOffsetMs 在正式服固定为 0，不参与服务端时间计算。

### 2.5 kr_game_wallet：唯一资源余额

user_id 为主键；gold JSON；diamonds BIGINT UNSIGNED；star_gems BIGINT UNSIGNED；ruby JSON；pet_coins BIGINT UNSIGNED；adventure_tickets INT UNSIGNED；adventure_cores JSON；create_time/update_time。

gold/ruby 是 {digits, exponent, precision}；其余整数和 cores 每项保持现有安全整数约束。所有操作检查非负、溢出、玩法上限及当前规则；配置下调不能把有效旧余额判为坏档。

DTO 组装时映射回 money、weapons.diamonds、weapons.starGems、rebirth.ruby、pets.coins、adventure.tickets、adventure.cores。这些值不再在 state_json 保存另一份可写副本。

### 2.6 kr_game_request：幂等回执

user_id、request_id VARCHAR(64)、action VARCHAR(64)、payload_hash CHAR(64)、http_status、result_json JSON、result_revision BIGINT、create_time。

主键或唯一索引：(user_id, request_id)。payload_hash 基于规范化的 action、业务参数、期望版本，以及影响资格的已验证身份上下文计算；不包含原始 token。请求编号在同一用户全部写接口中唯一。

一次成功业务与回执在同一事务提交，不在事务外先写永久 processing 状态。并发相同请求由玩家行锁串行化。事务已提交而响应失败时可读取回执；相同编号不同参数返回 REQUEST_ID_CONFLICT。

永久保留最小去重键。大响应可归档，但归档后返回已处理状态或结果引用，不能把旧 request_id 当新请求再次执行。业务失败一般不持久化成功回执；允许在条件变化后重新请求，但仍受业务领取唯一约束限制。

### 2.7 kr_game_ledger：资源流水

id、user_id、request_id、action、biz_key、currency、before_value JSON、delta_value JSON、after_value JSON、config_version、source_provider、create_time。

同一命令中同一种资源先汇总，再写一条流水；唯一索引 (user_id, request_id, currency)。amount JSON 明确区分 int 与 inf 类型；inf 类型保留 digits/exponent/precision 和有符号增量。查询索引 (user_id, id)。

成功的资源变更必须有流水，免费且不改变资源的命令可以只有回执。管理员补偿、初始化和旧档导入也使用明确的 action/biz_key。流水不代替当前钱包，但可用于核对与追溯。

### 2.8 kr_game_checkin_claim：签到明细

id、user_id、activity_id VARCHAR(64)、business_date DATE、day_index INT、total_check_num、reward_json JSON、config_version、request_id、create_time。

唯一索引：(user_id, activity_id, business_date)。activity_id 表示稳定的签到活动，不能每次配置发布重新生成。day_index 由服务器决定，实际奖励与当时配置记录在 reward_json。

当前累计七次循环；没有连续天数清零规则。state_json.dailyCheck 与明细、钱包在同一事务更新。

### 2.9 kr_game_redeem_batch：兑换批次

id、name、status、starts_at_ms、expires_at_ms（可空）、allowed_providers JSON、reward_preset_id、config_version、max_uses（可空）、used_count、per_user_limit、created_by、create_time/update_time。

初版 per_user_limit 固定为 1。奖励预设和配置版本绑定后不可在有领取记录时直接覆盖；需要变更奖励时新建批次。活动停用、时间调整走后台服务并记录审计。

### 2.10 kr_game_redeem_code：兑换码

id、batch_id、code_digest CHAR(64)、display_suffix、status、max_uses（可空）、used_count、create_time/update_time。

code_digest 唯一，建议对规范化码使用服务器 HMAC 摘要。规范化第一版仅去首尾空白，避免改变旧码语义；后续改大小写规则需版本化。低熵旧码不能只靠“哈希后没人知道”当作保护，应限制失败尝试。

公共码 max_uses 可为空或指定总量；单次码 max_uses=1。后台生成时一次性输出明文，默认不在普通列表、日志中回显。摘要密钥作为可恢复的部署密钥管理，轮换时设计兼容查找方案，不能直接丢弃旧密钥导致所有码失效。

### 2.11 kr_game_redeem_claim：兑换明细

id、user_id、batch_id、code_id、reward_json JSON、config_version、request_id、source_provider、create_time。

初版唯一索引：(user_id, batch_id)，保证同一批次的不同码也只能领一次；另设 (code_id, user_id) 唯一索引以明确单码语义。

批次总额度和单码额度都在锁定相应行后检查并增加 used_count。禁止在事务外查询“还有名额”然后直接发奖。

### 2.12 kr_game_admin_audit：运营操作审计

id、manager_id、action、target_type、target_id、reason、before_json、after_json、request_id、create_time。

兑换批次/码的创建和停用、封禁、补偿、迁移批准都记录。敏感身份凭证、原始 token 和明文兑换码不写 before/after。经济操作对应审计与流水关联；业务成功与审计尽量同事务提交，不写进 MyISAM 异常表充当业务审计。

### 2.13 kr_game_save_import：旧档迁移申请

id、user_id、source_hash、source_backup_ref、status、migration_version、approved_by、decision_json、completed_request_id、create_time/update_time。

user_id 唯一，保证每个账号最多一个迁移生命周期；重试更新同一申请，不新建第二次导入。原档备份在服务端非公开存储，备份引用不能成为玩家可任意读取的文件路径。

source_hash 用于重复提示与审计；不能全局唯一地判定账号归属，因为两个正常新档也可能内容相同。导入是否允许取决于账号资格和迁移政策。完成迁移与初始余额调整、领取标记、流水、申请完成状态原子提交。

### 2.14 后续正式经济结算必需：kr_game_run

run_id、user_id、mode、status、config_version、start_state_revision、trusted_start_state JSON、started_at_ms、expires_at_ms、settled_request_id、settled_result JSON。

run_id 唯一，玩家 state 行记录当前有获奖资格的 active_run_id，由同一锁控制并发场次。模式切换和重连按明确规则恢复或关闭旧场次。服务端确认的中途升级/换装关联到 run 的事件或版本记录，不能忽略这些变化。

status 从 started 到 settled/expired/cancelled 单向变更。settled_result 和发奖同事务提交；不得让客户端重置场次。旅行行程和离线结算同样需要稳定的业务编号与不可重复结算状态。

## 4. API 列表

公共前缀 /game/v1。成功沿用项目直接返回 JSON 对象的风格，不额外套一层与现有项目不同的 code=0。失败使用 HTTP 状态与 {code, message, detail}。

| 方法与路径 | 输入 | 行为 |
|---|---|---|
| POST /auth/wechat | code、服务端配置别名 | 验证微信身份并签发游戏会话 |
| POST /auth/taptap | code、服务端配置别名 | 验证 TapTap 小游戏身份并签发会话 |
| POST /auth/logout | Bearer | 撤销当前会话 |
| GET /bootstrap | Bearer | 同一快照返回 UID、服务器时间、配置和完整存档 |
| GET /state | Bearer | 拉取最新权威状态 |
| PATCH /preferences | request_id、expected_revision、白名单偏好 | 保存无经济影响的账号偏好 |
| GET /checkin | Bearer | 返回当前业务日、奖励展示、可领取项 |
| POST /checkin/claim | request_id | 服务端决定当天可领取项并发奖 |
| POST /redeem/claim | request_id、code | 校验并兑换 |
| GET /requests/:request_id | Bearer | 查询当前 UID 的操作回执 |
| POST /commands | request_id、expected_revision、action、payload | 调用白名单业务处理器 |
| POST /runs/start | request_id、expected_revision、mode | 校验资格并创建玩法场次 |
| POST /runs/settle | request_id、run_id、结果证据 | 计算和提交允许的收益 |
| POST /offline/settle | request_id | 根据服务器时间与游标计算离线进度 |
| POST /save-import | request_id、旧档、迁移资格凭证 | 受控申请或执行一次性迁移 |

路由只接受表列方法。除登录外均要求 GameAuth。登录中的配置别名必须是服务器预置且启用的白名单；不能传任意平台地址、AppSecret 或测试环境参数。

commands.action 显式注册到处理器，例如 weapon.draw、weapon.merge、weapon.equip、weapon.star、upgrade.buy、skin.buy、skin.select、pet.draw、pet.merge、pet.equip、fish.draw、fish.merge、rebirth.start、adventure.start、adventure.claim、relic.draw、relic.upgrade、raid.mission.claim。不得用 action 拼接任意 PHP 类名或方法名。每项独立验证参数、规则、事务与权限。

API 列表是目标契约：run、offline 和未完成的命令在对应实施阶段开启，不能先提供信任客户端结果的空壳。

## 5. 请求与结果示例

签到不提交奖励金额、设备日期或 UID：

~~~json
{
  "request_id": "8a877e1c-1f4f-4665-a209-661fb3483153"
}
~~~

成功响应示例，数值只用于说明现有第一天奖励与 revision 形式：

~~~json
{
  "request_id": "8a877e1c-1f4f-4665-a209-661fb3483153",
  "revision": "43",
  "config_version": "economy-release-example",
  "business_date": "2026-10-23",
  "result": {
    "action": "checkin.claim",
    "day_index": 0,
    "reward": { "diamonds": 140 }
  },
  "wallet": {
    "diamonds": 2140
  },
  "changed": {
    "dailyCheck": {
      "lastClaimDay": "2026-10-23",
      "checkNum": 1,
      "totalCheckNum": 1
    }
  }
}
~~~

实际响应还包含 server_time_ms。wallet/changed 是带 revision 的权威更新；如果客户端基础 revision 与本次变化不连续，先 GET /state，再展示最新余额。历史回执不覆盖更新的本地权威缓存。

结构性操作示例：

~~~json
{
  "request_id": "b66f29d6-201d-49a5-8597-765c5cccf4c0",
  "expected_revision": "43",
  "action": "weapon.equip",
  "payload": {
    "from": { "kind": "backpack", "index": 3 },
    "to": { "kind": "equipment", "index": 0 }
  }
}
~~~

装备位置必须在该 revision 的服务器库存中解析；客户端提供武器 ID 或属性不能成为拥有证明。

冲突响应，HTTP 409：

~~~json
{
  "code": "STATE_CONFLICT",
  "message": "存档已更新，请同步后重试",
  "detail": { "current_revision": "44" }
}
~~~

| HTTP | 业务码 | 客户端动作 |
|---|---|---|
| 401 | GAME_TOKEN_EXPIRED / GAME_TOKEN_INVALID | 重新平台登录，再查询未确认的原请求 |
| 403 | PLAYER_DISABLED / CHANNEL_NOT_ALLOWED | 停止对应操作，显示服务器原因 |
| 409 | STATE_CONFLICT | 获取最新状态，重新确认操作意图，使用新编号提交 |
| 409 | REQUEST_ID_CONFLICT | 不重用该编号发送另一组参数 |
| 409 | CHECKIN_ALREADY_CLAIMED / REDEEM_ALREADY_CLAIMED | 同步状态，显示已领取；相同 request_id 重试优先返回原成功 |
| 409 | RUN_ALREADY_SETTLED / SAVE_IMPORT_NOT_ALLOWED | 查询原结果或停止迁移 |
| 422 | VALIDATION_ERROR / INSUFFICIENT_RESOURCE / CODE_INVALID | 修正输入或更新界面 |
| 429 | TOO_MANY_REQUESTS | 按服务器等待时间重试 |
| 503 | PLATFORM_UNAVAILABLE / TEMPORARY_FAILURE | 保留待确认操作；数据库提交结果不明时用原编号查回执 |

网络超时与“业务确定失败”必须区分。数据库提交结果不明不能显示确定未发奖，也不能为同一意图换一个新编号盲重试。

## 6. 提交与回滚示意

以下是事务边界示意，非已实现 PHP 代码：

~~~text
Controller:
  解析已认证 UID
  验证请求 DTO
  result = Service.execute(context, dto)
  success(200, result)                 // 事务外

Service.execute:
  transaction:
    锁 state
    读取回执；重复则返回已提交结果
    校验 expected_revision / 业务条件
    按统一顺序锁活动、码、钱包
    更新资源与模块
    写领取记录、流水、审计（如有）
    revision += 1
    写成功回执
    return result                     // 框架提交事务后才返回 Controller
~~~

普通校验失败抛业务异常并由接口层映射响应。现有 ExceptionHandle 会把一般异常归为 500，因此新增 GameBusinessException 时应携带明确的 HTTP 状态与业务码，由 game 层映射到既有错误结构；所有游戏接口固定返回 JSON。事务中不调用第三方网络接口，不执行长时间文件上传，不调用 Send::success，也不嵌入会抛响应异常的 Controller 方法。

## 7. 迁移与部署约束

1. 确认真实数据库版本、表引擎、前缀及备份可恢复性；不直接重新导入 public/kr_bdf.sql 覆盖现有库。
2. 单独迁移 kr_user 引擎，验证原 wxapp/admin 行为；DDL 与发奖 DML 分开执行，不能假定 DDL 随业务事务回滚。
3. 创建游戏表和唯一索引；导入旧平台身份前先处理重复项并补全所属 appid。
4. 服务端只启用已完成的命令和配置版本；首期不开放任意存档覆盖接口。
5. 先接测试环境，运行真实 MySQL 并发与故障测试；SQLite 或 mock 不能代替 InnoDB 事务验收。
6. Cocos 对齐异步命令后执行 Project 要求的 npm run check，以及微信/TapTap 真机登录、重试与生命周期验证。
7. 数据结构优先向后兼容；回滚应用不能删除领取明细、流水和请求去重键。
8. 历史备份只能作为新 revision 的受审计恢复来源；恢复经济状态需要核对之后的资源流水，不能简单回放旧钱包。

待实施前确认的环境信息：真实 MySQL 版本、服务器可用 PHP 版本、两平台应用配置及 API 域名。产品默认值：未绑定渠道各自建号、现有七次循环签到、同批次兑换码每个 UID 一次、普通与广告收益数值保持当前配置。
